Architektura backendu (Flask & Databáze)

Architekturu serveru (backendu) jsme navrhli s ohledem na vysoký výkon, bezpečnost, odolnost proti výpadkům sítě a co nejnižší režii při komunikaci s databází a externími zdroji dat. Celou aplikaci pohání Python s mikroframeworkem Flask, spuštěný pod WSGI serverem Gunicorn.

Adresářová struktura projektu

webova_aplikace/
├── app.py                  # Hlavní Flask aplikace a definice API endpointů
├── menu_cache.py           # Asynchronní mezipaměť jídelníčků (daemon vlákno)
├── menu_collector.py       # Klient pro stahování dat z API WebKreditu
├── robot.py                # Synchronizační skript pro plnění databáze
├── utils.py                # Sdílené utility (DB pool, parser alergenů, slug)
├── gunicorn.conf.py        # Konfigurace WSGI serveru Gunicorn
├── requirements.txt        # Závislosti Python balíčků
├── Dockerfile              # Předpis pro sestavení Docker obrazu
├── init_db.sql             # Schéma a výchozí seznam jídel pro PostgreSQL
├── templates/
│   ├── index.html          # TV signage – hlavní prezentační rozhraní
│   └── test.html           # Diagnostická stránka (dbcheck)
└── static/
    ├── uploads/            # Nahrané fotografie pokrmů (persistentní volume)
    └── photos/             # Statické zástupné obrázky

Správa databázových připojení (Connection Pooling)

Abychom ušetřili systémové prostředky a vyhnuli se neustálému otevírání a zavírání TCP spojení k databázi při každém požadavku, implementovali jsme pool připojení. Využíváme k tomu třídu ThreadedConnectionPool z knihovny psycopg2:

# Inicializace ThreadedConnectionPool v utils.py (min 2, max 10 připojení)
_db_pool = pool.ThreadedConnectionPool(
    2, 10,
    host=DB_HOST, port=DB_PORT,
    database=DB_NAME, user=DB_USER, password=DB_PASS
)

Vlákna serveru a asynchronní workery si připojení půjčují metodou get_conn() a po dokončení práce ho v bloku finally bezpečně vracejí zpět přes release_conn(). Pokud transakce selže, zavolá se conn.rollback(), což zajistí integritu a konzistenci dat.

Asynchronní paměťová mezipaměť (menu_cache.py)

Chceme-li šetřit oficiální API WebKreditu a zaručit, že infopanely budou fungovat i při výpadku internetu, vytvořili jsme paměťovou mezipaměť (cache) v modulu menu_cache.py. Při startu Flasku se spustí samostatné daemon vlákno:

# Spuštění cache workeru jako daemon vlákna
t = threading.Thread(target=_worker, args=(app,), daemon=True, name="menu-cache-worker")
t.start()

Toto asynchronní vlákno na pozadí každých 30 sekund stahuje aktuální data ze všech sledovaných menz a ukládá je do paměťového slovníku _cache. Protože k mezipaměti přistupuje více vláken naráz (z infopanelů i z telefonů obsluhy), je přístup chráněn zámkem threading.Lock(), abychom předešli stavům souběhu (race conditions).

Pokud je mezipaměť po startu serveru prázdná, aplikace provede přímý dotaz na API WebKreditu (fallback), takže data jsou dostupná okamžitě bez čekání na první doběhnutí workeru.

Databázové schéma

Relační databáze PostgreSQL obsahuje tři hlavní tabulky propojené cizími klíči:

Tabulka Sloupec Typ Popis
categories id SERIAL PK Primární klíč kategorie
name VARCHAR(100) Název kategorie (Oběd, Minutka, Polévka…)
meals id SERIAL PK Primární klíč pokrmu
category_id FK → categories Odkaz na kategorii
original_name TEXT Originální český název
name_en TEXT Anglický překlad názvu
slug VARCHAR Unikátní ASCII identifikátor (bez diakritiky)
photos id SERIAL PK Primární klíč fotografie
meal_id FK → meals Odkaz na pokrm
file_path TEXT Relativní cesta k souboru (uploads/img_meal_*.jpg)
is_primary BOOLEAN Indikátor primární fotografie (zobrazená na TV)

Při nahrání nové fotky ke stejnému jídlu se u všech starších snímků automaticky vypne příznak is_primary a nová fotka se označí jako hlavní. Na televizních panelech pak zobrazujeme vždy pouze tuto nejnovější primární fotografii.

REST API – přehled endpointů

Metoda Endpoint Popis
GET / Hlavní stránka TV signage (Jinja2 šablona index.html)
GET /test Diagnostická stránka pro ověření stavu DB a API
GET /api/load-menu?canteen_id=X Jídelníček pro TV panel – vrací pokrmy s fotkami a cenami
GET /api/portions?canteen_id=X Aktuální počty zbývajících porcí pro danou menzu
GET /api/mobile/menu?canteen_id=X Jídelníček pro mobilní aplikaci – vrací pokrmy se stavem fotky
POST /api/mobile/upload Nahrání fotografie pokrmu (multipart/form-data)
POST /api/mobile/verify_pin Ověření přístupového PINu mobilní aplikace (JSON)

Všechny API endpointy vracejí data ve formátu JSON a obsahují patřičná CORS nastavení, aby na ně mohly bezpečně přistupovat infopanely i mobilní aplikace z různých síťových segmentů. Hlavičky odpovědí nesou bezpečnostní direktivy (např. X-Content-Type-Options, X-Frame-Options).

Parsování kódů alergenů z textu

Oficiální univerzitní API neposkytuje alergeny ve sjednocené formě. Proto jsme v utils.py napsali vlastní parser parse_allergens využívající regulární výrazy. Ten funguje ve dvou režimech:

  • Přímé kódy: Pokud text obsahuje rovnou čísla alergenů (detekované výrazem \b(1[0-4]|[1-9][a-h]?)\b), parser je vytáhne regulárním výrazem.
  • Klíčová slova: Pokud čísla chybí, parser prohledává text na přítomnost klíčových slov pro všech 14 kategorií alergenů (např. „pšenice“ → 1a, „vejce“ → 3).

Ošetřili jsme i okrajové případy – například vyhledávání para ořechů (alergen 8f) chytře ignoruje slovo „parametr“, aby nedocházelo k falešným nálezům.

Automatizované testování: Správnost chování parseru alergenů a algoritmu na generování unikátních ASCII slugů trvale ověřuje sada 13 jednotkových testů v souboru test_utils.py. Testy lze spustit příkazem python -m pytest test_utils.py -v.

Bezpečnostní opatření

  • SQL Injection: Veškeré dotazy jsou parametrizované (zástupné znaky %s v psycopg2). Nikde nepoužíváme přímé spojování řetězců s uživatelskými vstupy.
  • Validace souborů: Nahrávané fotky kontrolujeme na povolené přípony (jpg, jpeg, png, webp) i skutečný typ (MIME type). Název souboru čistíme funkcí secure_filename().
  • HTTP hlavičky: Každá odpověď obsahuje bezpečnostní hlavičky (X-Content-Type-Options: nosniff, X-Frame-Options: SAMEORIGIN).
  • Izolace služeb: Databáze není přístupná zvenčí – komunikace probíhá výhradně uvnitř virtuální sítě Dockeru.
